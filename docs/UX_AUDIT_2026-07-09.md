# Audit UX / TUX / logique / conformité — SecOps Agent (2026-07-09)

> **Nature :** audit de *conventions et d'écarts*, benchmarké contre les trois références
> explicites du projet (Claude Code, Codex CLI, Antigravity `agy`) et contre quelques
> référentiels reconnus (clig.dev, OWASP Top 10 for Agentic Applications **2026**,
> spec MCP, PTES/WSTG/NIST SP 800-115). **Aucun fichier n'a été modifié.** Le livrable
> est ce rapport.
>
> **Ne duplique pas** les backlogs existants (`BACKEND_REVIEW_2026-06-28`,
> `BEHAVIORAL_AUDIT_2026-07-03`, `AUDIT_RELIVE_2026-07-04`, `IMPROVEMENT_PLAN_2026-06-29`).
> Ces docs traitent la *qualité conversationnelle* (leaks, timezone, parité FR, file
> d'entrée, duplication de rendu, P1–P6). Le présent audit attaque un axe différent :
> **alignement structurel sur les conventions agentiques et les référentiels de sécurité**.
> Les recoupements sont signalés explicitement (« déjà suivi en… ») pour éviter le doublon.

`Annoying`→**Moyen**, `Cosmetic`→**Cosmétique**, plus **Élevé** pour important-non-bloquant).

- **[MANQUANT]** — la fonctionnalité n'existe pas.
- **[MAL EXPOSÉ]** — la fonctionnalité existe mais est peu découvrable / sous-exploitée

## Phase 1 — Interface (TUI)

### Ce qui tient (vérifié, aucune action)
- **Séparation saisie / flux** : nette. Boîte de saisie encadrée par deux règles `─`,
  toolbar bas, flux d'outils au-dessus (`tui_smoke` confirme). Conforme Codex/agy.
- **Coloration syntaxique** : présente via `Markdown(..., code_theme="ansi_dark")`
  (`renderer.py:351,3097,3666`). Les blocs de code sont colorés.
- **Carte outil** : `● ToolName(arg)` + `⎿` collapsé + `ctrl+o` — fidèle agy
  (`tool_display.py:565`). Glyphe plein, état par couleur : décision de parité déjà actée.

### F1.1 — Le `risk_class` (r0–r8) n'est pas gradué visuellement `[MAL EXPOSÉ]`
- **Réf.** `tool_display.py:287` `_tool_status_color` ; `:565` `ToolCallBox.render` ;
  `:401` `_RISK_LABELS` ; `:414` `_approval_context_line`.
- **Observé.** Sur la carte outil en direct, la couleur est **binaire** : `is_dangerous`
  → jaune (`warning`), sinon `accent`. Un `dir_brute` (r3), un `webshell_exec` (r6) et un
  `generate_payload` (r6) rendent tous le **même `●` jaune**. Le label R (« R6 exploit
  assistance ») n'apparaît **que** dans l'écran d'approbation, jamais sur la carte
  d'exécution ; et un outil dangereux auto-autorisé (ex. `nmap_scan`, r3) n'affiche
  **aucun** label R puisqu'il ne déclenche pas d'écran d'approbation.
- **Écart.** Le brief exige « une action r5/r6 impossible à confondre avec une r0 ». Cette
  borne minimale est **tenue** (jaune vs accent). Mais la **gradation** r3→r6 — la plus
  utile pour un agent offensif — est absente de la surface la plus vue (la carte live).
  La taxonomie riche existe et est même labellisée : c'est un problème d'exposition, pas
  d'absence. Réf. : conventions Codex/agy (codage visuel du risque).
- **Sévérité** Moyen · **Effort** S–M.

### F1.2 — Aucune prévisualisation de plan approuvable avant exécution `[MANQUANT]`
- **Réf.** `core/planner.py` (le plan est recalculé à chaque tour puis jeté) ; aucune
  commande `/plan` (`ui/commands.py` — absente) ; `ARCHITECTURE.md` §4/§8 chantier 5 et
  `IMPROVEMENT_PLAN_2026-06-29.md` tâche 4.2 (**non faite**).
- **Observé.** L'approbation est **par-outil, à l'instant ACT** (`ApprovalPrompt`,
  `tool_display.py:799`) : correcte pour *une* action, mais l'utilisateur ne voit jamais
  la **trajectoire complète** (suite d'actions candidates) *avant* qu'elle démarre. Le
  `Plan` n'est pas un objet persistant sur le blackboard et n'est pas inspectable.
- **Écart.** Codex CLI affiche le plan de l'agent et permet d'approuver/rejeter **chaque
  étape en ligne** avant exécution ; c'est le repère explicite du brief. Ici on a des
  garde-fous d'exécution, pas une revue de plan. *(Partiellement suivi en 4.2 — mais 4.2
  ne couvre que l'objet `Plan`+`/plan` inspectable, pas la revue-avant-exécution façon
  Codex.)*
- **Sévérité** Élevé · **Effort** L.

### F1.3 — Statusline riche existante mais tronquée et sans coût `[MAL EXPOSÉ]`
- **Réf.** `input_handler.py:1083` `_build_statusline` (toolbar live réel) ; contraste avec
  `main.py` où de nombreuses surfaces overlay passent `status_right=friendly_model_name(...)`
  (modèle seul) ; `renderer.py:1847` `render_statusline` = *aperçu* `/statusline`, pas la barre.
- **Observé.** La barre live **porte déjà** modèle · état · phase · cwd · profil · sandbox ·
  permissions · `auto:{posture}` · tokens · tasks · dirs · tools — plus riche qu'agy. **Mais** :
  (a) sous 90 colonnes, `posture`, `permissions` et `phase` **disparaissent** (`:1099-1106`) —
  or ce sont justement les champs de sûreté ; (b) **aucun coût $ / usage monétaire** et pas
  de `/cost` ni `/status` (Claude Code les expose). Les tokens estimés couvrent partiellement
  « usage ».
- **Écart.** Claude Code : statusline persistante répondant en permanence *modèle / mode de
  permission / coût*. Ici le mode/posture est présent mais **fragile en largeur** et le coût
  absent.
- **Sévérité** Moyen · **Effort** S.

### F1.4 — `/artifact` & « structured scan progress » sous-exploités `[MAL EXPOSÉ]`
- **Réf.** `ui/renderer.py:1377` `render_artifacts` + `runtime.add_artifact`
  (`main.py:248,392,404,1172`) ; `core/tools.py:192` `report_progress`/`ToolProgress`.
- **Observé.** `/artifact` existe et liste des artefacts, **mais** ceux-ci ne sont créés
  qu'à quelques points (export/rapport de session), **pas auto-générés depuis les scans**.
  Un gros scan reste un flux d'appels d'outils + carte collapsée `ctrl+o` ; il n'y a pas de
  panneau d'artefacts persistant ni de « liste de tâches / plan » commentable en continu.
  Le `ToolProgress` est rendu de façon transitoire pendant l'exécution puis perdu.
- **Écart.** Antigravity « Artifacts » : sorties volumineuses vérifiables d'un coup d'œil,
  annotables **sans interrompre** l'exécution. La brique existe (registre d'artefacts) mais
  n'est pas branchée sur la sortie des scans → rôle non rempli.
- **Sévérité** Moyen · **Effort** M.

### F1.5 — Thème non sélectionnable `[MANQUANT]`
- **Réf.** `ui/theme.py:20` `COLORS` = palette unique (sombre) ; `code_theme="ansi_dark"`
  codé en dur. Aucun `light/dark`, aucun `prefers-color-scheme`, aucun sélecteur.
- **Écart.** Codex CLI : thème sélectionnable. Peu prioritaire pour un outil terminal
  offensif, mais c'est une vraie absence.
- **Sévérité** Cosmétique · **Effort** M.

## Phase 2 — Expérience (TUX)

### Ce qui tient (vérifié)
- **Découvrabilité des commandes** : `/help`, `/tools` (avec **risk class**, plus riche
  qu'agy), `/tool <name>`, palette slash à autocomplétion 2 colonnes haute-fidélité
  (`ui/commands.py`, confirmé `AUDIT_RELIVE §1`). Bon.
- **Confirmation avant l'irréversible** : l'écran d'approbation montre l'appel exact, la
  ressource, le risque, et permet d'**éditer la commande** (`e`) avant exécution
  (`tool_display.py:458,887`). Conforme clig.dev / agy.

### F2.1 — Commande inconnue : erreur plate, sans suggestion « did you mean » `[MAL EXPOSÉ]`
- **Réf.** `main.py:1566` `render_error(f"Unknown command: {cmd}")`. Le registre complet
  `COMMANDS` (`ui/commands.py`) et `difflib.get_close_matches` sont disponibles ; aucun n'est
  utilisé.
- **Observé.** `/exot` → « Unknown command: /exot », rien d'autre.
- **Écart.** clig.dev (human-first) : sur erreur, **suggérer la correction / la commande
  suivante**. La donnée existe, l'affordance non.
- **Sévérité** Moyen · **Effort** S.

### F2.2 — Pas de « plan mode » (exploration à coût nul) `[MANQUANT]`
- **Réf.** Recherche `plan_mode`/`/plan` → **néant**. Les modes de permission
  (`request-review / proceed-in-sandbox / always-proceed / strict`,
  `cli/permissions.py:11`) sont des **gates par-outil**, pas un espace d'exploration.
- **Observé.** On peut baisser/monter les permissions, mais il n'existe pas de mode où
  l'agent **planifie et raisonne sans émettre aucun appel d'outil risqué** avant une
  exécution réelle.
- **Écart.** Le « plan mode » de Claude Code = espace d'exploration à coût nul, zéro appel
  d'outil risqué, *avant* toute exécution. Distinct des modes déclaratifs présents ici.
  (Recoupe F1.2 côté finalité.)
- **Sévérité** Élevé · **Effort** M–L.

### F2.3 — Les scans actifs frappent une cible réelle sans confirmation par défaut `[MAL EXPOSÉ / divergence]`
- **Réf.** `core/permissions.py:148-157` `rules["tool"]` ; vérifié à froid (settings isolé) :
  `nmap_scan → allow`, `subdomain_enum → allow` ; `dir_brute/http_request/webshell_exec/
  write_file/generate_payload → ask`.
- **Observé.** `nmap_scan` (r3 `ACTIVE_ENUMERATION`, `dangerous=True`) et `subdomain_enum`
  (r3) **s'exécutent contre une cible distante réelle sans aucune approbation** par défaut.
  L'utilisateur voit la carte *après* le lancement.
- **Écart.** (1) **Question transversale du brief** — « à tout instant, l'utilisateur
  sait-il ce qui va arriver à une cible réelle *avant* que ça arrive ? » : **non** pour
  l'énumération active. (2) **Contradiction doc/code** : `README.md:175` affirme que
  `nmap_scan … require approval`, ce qui est **faux** par défaut. (3) Principe de *moindre
  agence* (OWASP Agentic, ci-dessous). C'est un choix de vitesse assumable, mais non
  documenté et non aligné.
- **Sévérité** Élevé · **Effort** S (changer le défaut) — mais c'est une **décision de
  politique** à trancher, pas un bug.

### F2.4 — `/permissions allow tool(<r5/r6>)` persiste sans garde `[MAL EXPOSÉ / incohérence]`
- **Réf.** `cli/permissions.py:34-58` `parse_permission_argument`/`plan_permission_command`
  — accepte n'importe quel `allow tool(<name>)` sans contrôle de risque. À comparer avec
  `tool_display.py:500` `_approval_options` qui **retire volontairement** l'option
  « Persist » pour `_SHELL_TOOL_SESSION_ONLY` (run_shell, nmap_scan, dir_brute…).
- **Observé & preuve live.** Le `~/.secops_agent/settings.json` de cette machine contient
  `"tool(run_shell)": "allow"` — un allow-tout persistant pour l'exécution shell (r5). Or
  l'UI d'approbation **refuse d'offrir** cette persistance ; elle n'a pu être posée que via
  `/permissions allow tool(run_shell)`, qui **contourne** la divergence sécurité voulue.
- **Écart.** Deux chemins d'octroi de permission avec des politiques opposées → la garde
  R11 (`_approval_options`) est annulée par la CLI. La statusline n'indique que « perm N
  rules », sans mettre en évidence qu'un outil r5 est en allow persistant.
- **Sévérité** Moyen–Élevé · **Effort** S.

## Phase 3 — Logique métier / raisonnement

> Recoupé avec `BACKEND_REVIEW`/`IMPROVEMENT_PLAN` : la séparation plan→mémoire→autorité,
> le chaînage `pauses_for`, et le split parser (4.1) y sont déjà traités. Je complète.

### F3.1 — Les leçons `unreviewed` atteignent le contexte LLM via le briefing `[MAL EXPOSÉ / écart d'invariant]`
- **Réf.** `core/experience.py:558` `can_influence` (= `status in {"applied",
  "explanation-only"}`) ; `:1084` `retrieve_similar_lessons` filtre sur `can_influence` ;
  `:1162-1168` — une leçon **non revue** avec score suffisant reçoit le statut
  `explanation-only` (donc `can_influence = True`) ; `agent.py:842` `_relevant_lessons_briefing`
  → `store.retrieve()` → injecte `lesson.reason()` dans `ctx_str` (`agent.py:1652-1654`).
- **Observé.** L'**isolation d'autorité est solide** : `experience.py` n'a **aucun** chemin
  `registry`/`.execute`/`PermissionEngine` ; le *hard effect* (boost/downrank d'une
  `NextAction`) est bien gaté sur `is_reviewed` (`:1214-1217`). **Mais** le **texte** d'une
  leçon `unreviewed` — auto-écrite depuis une sortie d'outil (`build_lesson_from_tool_result`,
  `agent.py:569`) — est **injecté dans le contexte du modèle** (étiqueté « (unreviewed,
  explanation only) » + « Treat these as hints only »). C'est un canal d'**influence douce**
  du raisonnement *avant* validation humaine.
- **Écart.** `ARCHITECTURE.md §5.2` : leçons « écrites `unreviewed` et **mises en quarantaine**
  jusqu'à promotion humaine ». La quarantaine tient pour l'**autorisation** et le **rerank
  déterministe**, mais **pas** pour l'entrée dans le prompt. Cf. OWASP Agentic **ASI06
  Memory & Context Poisoning** (Phase 4) : une sortie d'outil attaquant-adjacente peut
  devenir une leçon `unreviewed` qui oriente un tour ultérieur. *(Les leçons `blocked`/
  `deprecated`/expirées sont bien exclues — `is_active` → rejet.)*
- **Sévérité** Moyen · **Effort** S (filtrer `is_reviewed` dans le briefing, ou rendre
  explicite que seules les leçons revues entrent en contexte).

### F3.2 — Angles morts d'OBSERVE : 19/38 outils sans parser dédié `[MANQUANT]`
- **Réf.** `core/result_parser.py:48` `_PARSERS` (19 entrées) → tout le reste tombe sur
  `parse_generic_output` (`result_parsers/system.py:123`, résumé texte, **ne peuple pas**
  `hosts_discovered`/`services_discovered`).
- **Observé — outils SANS parser dédié** (fallback générique) :
  `connect_vpn_config, disconnect_vpn, exploit_info, file_analyze, find_files,
  generate_payload, hash_generate, hash_identify, lab_setup_check, log_analyze,
  password_strength, ping_host, port_check, subdomain_enum, sysinfo, tech_detect,
  traceroute, vpn_status, waf_detect`.
  Parmi eux, ceux qui **devraient nourrir le blackboard mais ne le font pas** (vrais angles
  morts de mission, chacun signalé comme risque connu dans `CLAUDE.md`) :
  **`subdomain_enum`** (r3 — découvre des hôtes), **`tech_detect`** (r2 — technos/services),
  **`waf_detect`** (r3 — présence WAF = finding), **`port_check`** (r2 — ports/services),
  **`ping_host`** (r2 — vivacité d'hôte), **`traceroute`** (r2), plus **`file_analyze`/
  `log_analyze`/`find_files`** (r4 — preuves forensiques). Les autres (`hash_*`,
  `password_strength`, `vpn_status`, `sysinfo`, `lab_setup_check`) sont acceptables en
  générique (calcul pur ou déjà couverts par les réponses déterministes du preflight).
- **Écart.** `CLAUDE.md`/`ARCHITECTURE §6` : « un outil sans parser ⇒ angle mort de l'étape
  OBSERVE ». Le split 4.1 est fait ; la **couverture** n'a pas été étendue au-delà de
  l'existant. Un `subdomain_enum` qui trouve 8 sous-domaines n'ajoute **aucun** hôte au
  blackboard.
- **Sévérité** Moyen · **Effort** M.

### F3.3 — Le DENY sur chemins système de `write_file` est du code mort `[MANQUANT / autorité]`
- **Réf.** `core/permissions.py:383-385` : `evaluate_tool_arguments` fait `return decision,
  self.tool_resource(...)` **avant** les heuristiques fichier des lignes 387-397
  (inatteignables) ; `:423` `tool_argument_resource` ne mappe **que** `file_analyze/
  log_analyze/find_files` → `read_file`, jamais `write_file`.
- **Observé.** Les règles `rules["write_file"]` (`/etc`, `/bin`, `/usr` → **DENY**,
  `:163-167`) ne sont **jamais consultées** pour l'outil `write_file`. En pratique
  `write_file` retombe sur `TOOL_TIERS["write_file"] = ACTIVE` → **ASK** : donc pas d'écriture
  silencieuse, mais le **DENY dur** défense-en-profondeur sur les chemins système est
  contourné — un `write_file` vers `/etc/passwd` obtient un simple ASK approuvable, pas un
  refus catégorique.
- **Écart.** Séparation des pouvoirs / OWASP Agentic **ASI02 Tool Misuse**. C'est un bug de
  code (retour avant la branche), pas une porte ouverte — mais une dégradation réelle de la
  défense en profondeur.
- **Sévérité** Moyen · **Effort** S.

### F3.4 — Garde-fous de convergence robustes aux répétitions exactes, pas au « no-progress » `[MAL EXPOSÉ]`
- **Réf.** `agent.py:1695` `while iteration < self.max_iterations` (=14) ; `:1809` skip du
  doublon *intra-itération* ; `:1899-1906` arrêt sur streak ≥ 2 d'appels **identiques**.
- **Observé.** Solide pour les répétitions **strictement identiques**. Mais la signature
  d'appel ne capture pas : (a) une **alternance** A,B,A,B… (deux outils qui se relancent) ;
  (b) un **jitter d'arguments** (même outil, args trivialement différents — flag en plus,
  ordre changé). Ces deux cas peuvent **consommer les 14 itérations** sans progrès (coûteux
  sur un tier Gemma sujet aux 500, cf. E2 déjà suivi).
- **Écart.** Un détecteur « pas de progrès » fondé sur le **delta d'état du blackboard**
  (aucun host/service/finding nouveau depuis N tours) serait plus robuste qu'une égalité de
  signature. Cf. OWASP Agentic **ASI08 Cascading Failures**. Non couvert par le backlog.
- **Sévérité** Faible · **Effort** M.

## Phase 4 — Alignement sur des référentiels reconnus

### F4.1 — Cartographie OWASP Top 10 for Agentic Applications **2026** (ASI01–ASI10)
Mappé contre l'implémentation **réelle** (`risk_class` r0–r8, `AutonomyPolicy`,
`PermissionEngine`). Principe transverse évalué : **la moindre agence** — l'autonomie
doit se mériter.

| ASI (2026) | Couverture réelle | Écart / constat |
|---|---|---|
| **ASI01 Agent Goal Hijack** | `scope_guard`, `RequestDecision.scope_status`, planner contraint phase/scope, contraintes scope dures dans le prompt | **F4.3** : l'`EnvironmentHint` escalade l'autonomie sur **mots-clés du prompt** (non authentifiés). Pas de garde explicite contre l'injection indirecte via sortie d'outil. |
| **ASI02 Tool Misuse & Exploitation** | `risk_class` + `PermissionEngine` + `ActionTier` (fort) | **F2.3** (nmap/subdomain auto-ALLOW) ; **F3.3** (DENY write_file mort). |
| **ASI03 Identity & Privilege Abuse** | r5 privileged, `sudo.py`, ASK sur sudo | **r8 `CREDENTIALED_REMOTE_OR_IDENTITY_ACTION` défini mais assigné à AUCUN outil** (`tools.py:59`) ; aucun gate d'identité dédié ; un futur outil MCP à action créditée serait classé r7 (supply-chain), pas r8. |
| **ASI04 Supply Chain Compromise** | `MCPServerConfig.trust_status` (pending_review/hash_changed/trusted), `server_hash` SHA256, skills content-hash-gated, MCP `dangerous=True` | **Bien couvert.** |
| **ASI05 Unexpected Code Execution** | `sandbox.validate_exec_command`, gating `run_shell`, `scope_guard` | Couvert. |
| **ASI06 Memory & Context Poisoning** | leçons `unreviewed` par défaut, `/lessons`, `is_reviewed` gate le hard-effect | **F3.1** — le texte des leçons `unreviewed` (auto-écrites depuis sortie d'outil) entre dans le contexte LLM. Exposition ASI06 la plus directe. |
| **ASI07 Insecure Inter-Agent Comm.** | Pas de protocole A2A ; `.agents/agents/` = profils, MCP = client stdio | Largement **N/A** (mono-agent). À revisiter si A2A ajouté. |
| **ASI08 Cascading Failures** | garde-fous convergence + retry/timeout | **F3.4** (alternance/jitter) ; storm 500 (E2 déjà suivi). |
| **ASI09 Human-Agent Trust Exploitation** | écran d'approbation par-outil, labels de risque | **F1.2/F2.2** — l'humain approuve outil-par-outil mais ne voit jamais la trajectoire complète avant qu'elle démarre. |
| **ASI10 Rogue Agents** | `AutonomyPolicy` plafonne l'autonomie, séparation des pouvoirs testée | Couvert par conception. |

**Verdict moindre-agence.** Le défaut `risk_based` (recon bas-risque en chaîne, high-risk
en pause) est sain. Deux entorses : (1) l'énumération active auto-exécutée (**F2.3**) ;
(2) l'escalade d'autonomie pilotée par texte utilisateur (**F4.3**). L'autonomie n'est donc
pas *toujours* « méritée » — elle peut être accordée par simple phrasage.

### F4.2 — Client MCP figé sur un protocole ancien `[MANQUANT / conformité]`
- **Réf.** `core/mcp.py:104` `protocolVersion: "2024-11-05"` ; `:532` `_format_mcp_tool_result`
  (texte uniquement).
- **Observé vs spec courante.** La révision courante de la spec MCP est **2025-11-25**
  (précédée de 2025-06-18). Le client est **2–3 révisions en retard**. Manquent notamment :
  **structured tool output** (`outputSchema`/`structuredContent` — le client ne lit que le
  `content` texte, donc pas de chaînage fiable outil→outil) ; **elicitation** (serveur
  demandant une info à l'utilisateur en cours d'appel) ; **resource links** dans les
  résultats. Les `readOnlyHint`/`destructiveHint` ne sont pas exploités *(divergence déjà
  ratifiée en ADR — `IMPROVEMENT_PLAN` : gate in-process plus fort ; **ne pas re-planifier
  ce point**)*. OAuth/RFC 8707 = transport HTTP → **N/A** en stdio.
- **Écart.** Conformité à la version courante (au-delà du « ça marche ») : version épinglée
  obsolète + absence de sortie structurée.
- **Sévérité** Moyen · **Effort** M.

### F4.3 — Escalade d'autonomie pilotée par mots-clés non authentifiés `[MAL EXPOSÉ / design]`
- **Réf.** `core/request_context.py:287` `_environment_hint` (marqueurs `ctf`, `flag`, `htb`,
  `lab`, `room`, `user.txt`…) → `core/autonomy.py:46` `for_environment` → CTF/LAB escaladent
  à `SUPERVISED`.
- **Observé.** Un prompt contenant « flag » ou « lab » **élève l'autonomie** (moins de
  pauses) sur la seule foi du texte utilisateur, sans contexte vérifié.
- **Écart.** Moindre agence (ASI01/ASI03) : l'autonomie devrait se mériter sur un signal
  fiable, pas sur un substring. Un objectif détourné ou une cible client mal phrasée peut
  hériter d'une posture trop permissive.
- **Sévérité** Moyen · **Effort** S–M.

### F4.4 — Couverture des phases de pentest : post-exploitation structurellement fine `[MANQUANT — phase]`
Mappé contre PTES / OWASP WSTG / NIST SP 800-115 (les 38 outils enregistrés) :

| Phase | Outils réels | Verdict |
|---|---|---|
| Reconnaissance | dns/whois/http_headers/tech_detect/ssl_check/subdomain_enum/ping/port_check/traceroute/cve_lookup/fetch_url | **Complet** |
| Scan / énumération | nmap/dir_brute/ffuf/nikto/nuclei/sql_injection/xss/waf_detect | **Complet** |
| Analyse de vulnérabilités | cve_lookup/searchsploit/exploit_info/nikto/nuclei/ssl_audit | **Bon** |
| Exploitation | generate_payload/start_listener/webshell_exec/http_request/write_file/run_shell | **Moyen** (primitives génériques) |
| **Post-exploitation** | *(rien de dédié)* — seulement run_shell/webshell/write_file + find_files/file_analyze | **PHASE FINE** : pas d'énum de priv-esc, pas d'accès aux identifiants, pas de mouvement latéral, pas de persistance, pas d'exfiltration. |
| Reporting | `core/reporting.py` (module) | **Non exposé comme capacité d'agent** : pas d'outil `report` dans le registre ; la phase existe en code mais n'est pas une action planifiable de la boucle. |

- **Écart.** Le brief demande de signaler toute **phase structurellement absente**. La
  **post-exploitation** est la phase fine : au-delà d'un shell générique, l'agent n'a pas
  d'outillage pour la phase 6 PTES. Le **reporting** existe en module mais n'est pas une
  capacité de première classe du loop.
- **Sévérité** Moyen · **Effort** L (la post-ex est un chantier large).
